# 11 自我进化 · 学习笔记

> 核心问题：agent 如何从反馈中更新规则、skills 或工具策略，并避免污染长期上下文？
> 证据来源：`agent-session.ts`、`resource-loader.ts`、`extensions/runner.ts`、`messages.ts`、`session-manager.ts`、`examples/extensions/prompt-customizer.ts`、`dynamic-tools.ts`、`plan-mode/index.ts`。
> 一句话：pi 没有内置“评估 -> 修改 -> 验证 -> 回滚”的自我进化闭环。它提供的是可被应用层控制的更新面：临时 system prompt、资源 reload、动态工具、active tools、custom state 和 session 留痕。

---

## 题眼：自我进化不是让模型随便改自己

这里的“自我进化”更准确地说，是应用层根据反馈改进 agent 行为：更新规则、调整工具策略、沉淀 skill、记录状态，并在验证后固化。

当前 pi 源码里没有专门的自我进化模块，也没有通用 eval、reward、自动回滚、长期反馈学习器。相关能力要靠 extension、resource loader、session 和外部验证系统组合。

所以要把两件事分开：
- pi 提供哪些可更新的表面。
- 应用层怎么判断该不该更新，以及怎么验证和回退。

---

## 一、自我进化闭环的四步

| 步骤 | 做什么 | pi 提供 | 应用层要补 |
|---|---|---|---|
| 评估 | 判断当前行为哪里不好 | 事件流、session 历史、工具结果、用户输入 | 指标、反馈识别、人工确认、失败归因 |
| 更新 | 改 prompt、skill、工具集、模型策略 | 多个运行时更新面，见下文 | 生成修改方案、写文件、版本化 |
| 验证 | 确认修改有效且没副作用 | 可运行命令、extension 可触发流程 | eval 集、回归测试、对比策略 |
| 回滚 | 改坏后退回旧版本 | session append-only 留痕；reload 可重载旧资源 | 资源版本管理、回退触发、冲突处理 |

pi 主要覆盖“能在哪里接入”和“能改哪些运行时表面”；闭环控制本身不内置。

---

## 二、可更新面一：临时 system prompt

`before_agent_start` 发生在用户输入展开后、agent loop 前。handler 可以返回新的 `systemPrompt`：

```ts
pi.on("before_agent_start", (event) => {
  return { systemPrompt: event.systemPrompt + "\n..." };
});
```

runner 会把多个 extension 的返回值串联起来。`AgentSession.prompt()` 只在本轮使用这个 modified prompt；如果下一轮没有 extension 返回 prompt，就会重置回 `_baseSystemPrompt`。

这适合做试探性策略：先在一轮里加指导语，看效果，不急着写入文件。需要注意的是，`before_agent_start` 也能返回 custom message；custom message 进入本轮消息流，正常情况下会参与持久化和后续上下文，不应拿它存内部状态。

---

## 三、可更新面二：资源和 reload

`ResourceLoader` 有两个相关方法：

```ts
extendResources(paths): void
reload(): Promise<void>
```

`extendResources` 不是只登记路径。它会立刻把新路径合并到 `lastSkillPaths` / `lastPromptPaths` / `lastThemePaths`，并重新加载对应资源。真正让这些资源进入当前 system prompt 的地方，是 `AgentSession.extendResourcesFromExtensions()`：它在 `resources_discover` 后调用 `extendResources`，随后 `_rebuildSystemPrompt()`。

`session.reload()` 做得更重：
- 触发 `session_shutdown`，reason 是 `reload`。
- 重新加载 settings、资源、extensions。
- 重建 ExtensionRunner 和工具注册表。
- 如果已经绑定 UI/命令上下文，再触发 `session_start` 和 `resources_discover`。
- reload 后旧 ctx 会失效，不能继续用旧 command ctx 做后续操作。

因此，进化“规则和技能”的常见方式是：应用层修改 prompt/skill 文件，或者 extension 在 `resources_discover` 提供新路径，然后调用 reload 让资源重新进入运行时。

## 四、可更新面三：工具策略

工具有几层控制：
- 工具定义来自内置工具、SDK custom tools、extension `registerTool`。
- `tools` allowlist / `noTools` 决定哪些工具能进入注册表。
- active tools 决定当前模型实际可见的工具。

`setActiveToolsByName(toolNames)` 会：
1. 只保留注册表里存在的工具，未知名字忽略。
2. 更新 `agent.state.tools`。
3. 用新的工具列表重建 base system prompt。
4. 变化在下一次 agent turn 生效。

extension 也能动态 `registerTool`。`dynamic-tools.ts` 示例说明，session_start 或命令运行期都可以注册新工具；注册后还要经过 tool registry refresh、allowlist 和 active tools，才算真的可用。

这可以支持工具策略进化，例如临时禁用高风险工具、为某类任务启用专门工具、把失败率高的工具从 active tools 中移出。

## 五、可更新面四：状态和留痕

自我进化需要记住“为什么改、改了什么、验证结果如何”。pi 有两种容易混淆的 entry：

| API / entry | 是否进 LLM context | 适合存什么 |
|---|---|---|
| `appendEntry` / `custom` | 否 | 版本号、评估结果、外部资源 key、内部状态 |
| `sendMessage` / `custom_message` | 是 | 需要模型看到的扩展消息 |

如果目标是避免污染长期上下文，内部状态应放 `appendEntry`。`custom_message` 即使 `display:false`，也仍会被 `convertToLlm` 转成 user message 给模型看。

session tree 是 append-only，这有利于审计：可以回看哪个 turn 触发了更新、extension 存了什么状态、何时 reload。但 append-only 不等于自动回滚。真正的资源版本管理仍要靠应用层，比如 git、文件备份、外部 store 的版本字段。

## 六、一个可落地的自我进化设计

以下是基于 pi 原语的应用层设计，不是内置行为。

```text
1. 评估
  extension 监听 turn_end/message_end/tool_result
  -> 收集用户纠正、失败工具、重复操作、测试结果

2. 提议
  生成候选修改：prompt 规则、skill 内容、工具 active set
  -> 先写入 appendEntry 记录提议和理由

3. 试运行
  用 before_agent_start 临时修改 system prompt
  或临时 setActiveTools
  -> 不急着改磁盘基线

4. 验证
  跑固定 eval / 项目测试 / 用户确认
  -> 记录结果到 appendEntry

5. 固化
  修改 skill/prompt 文件或 settings
  -> session.reload()

6. 回滚
  如果验证失败或用户否决
  -> 还原旧文件/旧设置
  -> reload
```

这个设计的重点是把“试探”和“固化”分开。临时 prompt 和 active tools 适合试，磁盘上的 skill/prompt/settings 适合通过验证后再写。

## 与 Memory 篇的关系

Memory 和自我进化会用到同一批原语，但目标不同：

- Memory：把事实或偏好带进上下文，重点是检索和注入。
- 自我进化：改变 agent 之后的行为规则，重点是评估、验证和版本管理。

两者容易混在一起。一个经验规则是：给模型看的事实放 memory 注入；给系统自己用的学习状态放 `appendEntry`；通过验证后才把稳定行为沉淀成 prompt、skill 或工具策略。

---

## 一句话总结

pi 不内置自我进化闭环，但提供了足够的接入面：`before_agent_start` 做本轮 prompt 试验，`resources_discover` + `extendResources` + `reload` 更新资源，`registerTool` 和 `setActiveToolsByName` 调整工具策略，`appendEntry` 保存内部状态且不进上下文。是否更新、怎么验证、如何回滚，是应用层必须自己控制的部分。
