# 04b 多工具编排 · 学习笔记

> 核心问题：模型一个 turn 里返回多个 toolCall 时，pi 怎么编排？串行还是并行？并行"并"在哪一步？结果顺序和事件顺序分别怎么保证？有并发限制吗？工具很多时怎么办？toolResult 能保证什么？
> 证据来源：`packages/agent/src/agent-loop.ts`（`executeToolCalls` / `executeToolCallsSequential` / `executeToolCallsParallel` / `prepareToolCall` / `shouldTerminateToolBatch`）、`types.ts`（`executionMode`）。
> 一句话：一条 assistant 消息可含多个 toolCall。pi 默认并行，但**准备阶段（参数处理、校验、beforeToolCall）串行，真正执行阶段才并行**；任一工具声明 sequential 会让整批退化成串行；core 当前没有显式并发限制；toolResult 消息按模型原始顺序回传。toolResult 是工具执行产物，不是模型直接生成的内容，但 core 不负责判断结果语义上一定真实。

---

## 背景：04 tool 篇讲单个，这篇讲一批

04 tool 篇讲的是一个 toolCall 的一生（准备、执行、出错、结果回传）。但模型一次可以在 assistant 消息里返回多个 toolCall：

```ts
const toolCalls = message.content.filter((c) => c.type === "toolCall");
if (toolCalls.length > 0) { ... executeToolCalls(...) }
```

"一批 toolCall 怎么调度"是这篇补的内容。相关逻辑主要在 `agent-loop.ts` 的 `executeToolCalls` 几个函数里。

---

## 一、分派：整批串行还是并行（`executeToolCalls`）

```ts
const hasSequentialToolCall = toolCalls.some(
  (tc) => currentContext.tools?.find((t) => t.name === tc.name)?.executionMode === "sequential",
);
if (config.toolExecution === "sequential" || hasSequentialToolCall) {
  return executeToolCallsSequential(...);
}
return executeToolCallsParallel(...);
```

**决定规则**：两个条件任一成立就整批串行：
1. 全局配置 `config.toolExecution === "sequential"`（默认是 `"parallel"`）。
2. **这批里任何一个 tool 自己声明了 `executionMode: "sequential"`**。

这里的重点是：**单个工具能影响整批**。哪怕其它工具都能并行，只要有一个标了 sequential（如有副作用、不能与别的并发的工具），整批就会改为串行。这是偏保守的设计，优先避免并发风险。

`executionMode` 是工具可选声明的字段。内置工具当前没有标 `executionMode: "sequential"`；示例 extension 里 `tic-tac-toe.ts` 标了 sequential，用来避免多个棋盘工具调用同时改共享状态。

## 二、并行"并"在哪（`executeToolCallsParallel`）

并行分两阶段：

```ts
// 阶段1：for 循环里逐个 prepare —— 串行
for (const toolCall of toolCalls) {
  await emit({ type: "tool_execution_start", ... });
  const preparation = await prepareToolCall(...);   // await，串行
  if (preparation.kind === "immediate") { ...直接收集; continue; }
  // 阶段2的准备：把 execute 包成 async thunk 存进数组
  finalizedCalls.push(async () => {
    const executed = await executePreparedToolCall(preparation, ...);
    return await finalizeExecutedToolCall(...);
  });
}
// 阶段2：所有 execute 一次性并行
const orderedFinalizedCalls = await Promise.all(
  finalizedCalls.map((entry) => typeof entry === "function" ? entry() : Promise.resolve(entry)),
);
```

两阶段拆开看：
- **prepare 阶段（串行）**：`for` 循环逐个 `await prepareToolCall`。`prepareToolCall` 会找工具、运行 `prepareArguments`、校验参数，再调用 `config.beforeToolCall`。所以参数准备和权限拦截是一个一个过的。
- **execute 阶段（并行）**：prepare 完的包成 thunk，`Promise.all` 一次性全跑。真正耗时的执行（bash、读文件）才并行。

`prepareToolCall` 有一个 `immediate` 分支：工具不存在、参数校验失败、`beforeToolCall` 返回 block，都会直接变成错误 tool result。这类结果不进入 execute 阶段，但仍会参与后面的排序和 terminate 判断。

**对称的 afterToolCall**：finalize 阶段（`finalizeExecutedToolCall`:652）有 `config.afterToolCall`，执行后能改 `content/details/terminate/isError`。和 prepare 阶段的 `beforeToolCall` 一前一后，对应 extension 篇的 `tool_call`/`tool_result` 两事件。afterToolCall 自己也 try/catch，抛错转错误结果。

**为什么 Promise.all 不被单个异常影响整批**：`executePreparedToolCall`（604-638）内部 `try/catch`——工具执行抛异常，在**进 Promise.all 之前**就被 catch 成 `createErrorToolResult` + `isError:true`（632-637）。所以交给 `Promise.all` 的每个 thunk 都 resolve（错误也是 resolve 成错误结果），没有 reject，整批不会因此失败。"出错不影响其它"是这个写法保证的，不是偶然。

【判断，非源码注释】为什么 prepare 串行、execute 并行：拦截、参数修正和校验放在串行阶段，比较容易保持决策顺序；真正耗时的执行放到并行阶段，能减少等待。"准备串行、执行并行"是这套编排的重点。

（串行版 `executeToolCallsSequential` 则是 prepare + execute 都在一个 for 里顺序做，一个做完再下一个。）

## 三、事件顺序和结果顺序要分开

并行执行时有两种顺序：事件顺序和消息顺序。

先看消息顺序。回传给模型的 toolResult 消息顺序是稳定的：
```ts
const orderedFinalizedCalls = await Promise.all(
  finalizedCalls.map(entry => ...)   // map 保留原数组顺序
);
```
`Promise.all` + `map` 保留 toolCalls 的原始顺序。谁先跑完不影响 toolResult 消息次序。回传给模型的 toolResult 顺序 = 模型原始 toolCall 顺序。

事件顺序更细一点：
- `tool_execution_start` 在 prepare 阶段逐个发，所以 start 事件按原始 toolCall 顺序出现。
- `tool_execution_update` 来自各工具执行过程，并行时可能交错。
- `tool_execution_end` 在并行分支里由每个执行 thunk 自己 emit，谁先完成谁先发，所以 end 事件可能是完成顺序。
- `message_start/message_end` 的 toolResult 消息在 `orderedFinalizedCalls` 循环里发，所以按原始 toolCall 顺序出现。

这对 UI 很重要：UI 可以按执行事件显示实时进度，但给模型看的 toolResult 消息仍保持稳定顺序。

## 四、工具很多和并发限制

core 当前没有显式的并发池、信号量或分批逻辑。`Promise.all` 会把这一批已经 prepare 完的 execute 一次性放出去。模型返回 10 个可执行 toolCall，就会尝试同时执行 10 个。

注意分层：这里说的是 pi core（`packages/agent`）层。subagent extension（examples）自己另做了 max 8 任务、4 并发的限制，那是 extension 层的策略。

还要区分两种“多”：

- **可用工具很多**：主要影响模型选工具的难度和上下文成本。`executeToolCalls` 不负责给工具分组、裁剪或做动态注入。这通常要在 app/extension 层按场景只暴露需要的工具，或者给危险工具加权限检查。
- **一个 turn 里 toolCall 很多**：才进入本文的调度逻辑。pi core 没有显式并发上限，所以需要限制时，要靠 `toolExecution: "sequential"`、单个工具的 `executionMode: "sequential"`、`beforeToolCall` block，或者 extension 自己做队列、限流和最大任务数。

## 五、toolResult 的可信度边界

toolResult 不是模型直接生成的。正常情况下，它来自工具的 `execute` 返回；工具不存在、参数校验失败、执行抛错或 hook 抛错时，则由运行时转成错误结果。

pi core 能保证的是调用链路：工具名会被查找，参数会经过准备和校验，异常会转成 `isError: true` 的结果，结果会带着 `toolCallId/toolName/content/details` 回传，消息顺序也和原始 toolCall 对齐。

但 core 不保证结果内容在语义上一定真实。工具实现可能有 bug，外部命令或 API 可能返回旧数据，`afterToolCall` 还可以改写结果。更准确的说法是：toolResult 是工具执行产物，不是模型直接生成的内容；但它是不是可靠事实，要靠工具实现、结构化返回、错误标记、来源证据，以及上层必要的复核。

## 六、整批终止

```ts
function shouldTerminateToolBatch(finalizedCalls): boolean {
  return finalizedCalls.length > 0 && finalizedCalls.every((f) => f.result.terminate === true);
}
```
所有 toolResult 都标 `terminate === true` 才终止 loop。只要有一个不终止，loop 继续。单个工具的错误不终止整批，错误会变成一个错误结果回传。

---

## 核心链路

```text
assistant 消息含多个 toolCall
  -> executeToolCalls：判断整批串/并
     （config.toolExecution==="sequential" 或 任一工具 executionMode==="sequential" → 串行）
  -> 并行分支 executeToolCallsParallel：
      阶段1 for 循环逐个 prepareToolCall（找工具/参数校验/beforeToolCall）——串行
      immediate 分支：工具不存在/参数错误/被 block，直接生成错误结果
      阶段2 Promise.all(所有 execute)——并行，core 当前无显式并发限制
    -> execution update/end 事件可能按完成时机交错
    -> toolResult 消息按原始顺序 createToolResultMessage 回传
    -> toolResult 是工具执行产物，但事实可靠性取决于工具和上层校验
    -> shouldTerminateToolBatch：所有结果 terminate 才终止 loop
```

---

## 一句话总结

模型一个 turn 可返回多个 toolCall。pi 默认走并行分支，但真正并行的是 execute 阶段；prepare 阶段会串行完成找工具、参数处理、校验和 beforeToolCall。任一工具声明 sequential 会让整批转为串行。core 当前没有显式并发限制。并行时执行事件可能交错，但 toolResult 消息按模型原始顺序回传，所有结果都 terminate 才终止 loop。这套"准备串行、执行并行、结果有序回传"是 pi 工具编排的核心。工具很多时的规模控制、toolResult 的事实可靠性，则主要靠工具实现和 app/extension 层补上。
