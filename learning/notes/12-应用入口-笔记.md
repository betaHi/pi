# 12 Pi 应用与归一化入口 · 学习笔记

> 核心问题：怎么 build 一个 UI bot 或 CLI，把工作流归一化到一个 agent 入口？
> 证据来源：`packages/agent/src/agent.ts`、`packages/coding-agent/src/core/sdk.ts`、`agent-session.ts`、`agent-session-runtime.ts`、`main.ts`、`modes/*`、`packages/web-ui`、`examples/sdk/*`。
> 一句话：pi 的入口不是单层，而是三层：`Agent` 是 turn 引擎，`AgentSession` 加上模型、资源、工具、session 等设施，`AgentSessionRuntime` 再负责 active session 的重建和切换。CLI/TUI/RPC 复用 runtime，web-ui 直接复用 core Agent。

---

## 题眼：一个内核，多种外壳

前十篇讲的是内部机制：loop、tool、session、context、skill、extension。应用入口要回答的是：这些机制怎么被包装成 CLI、TUI、RPC、web 或自定义 bot。

pi 的分层大致是：

| 层级 | 作用 | 适合谁 |
|---|---|---|
| `new Agent` | 纯 turn 引擎，负责消息、工具调用、provider stream、队列 | 已有自己的存储、鉴权、UI，只需要 agent loop |
| `createAgentSession` | 装配 Agent、SessionManager、ModelRegistry、ResourceLoader、工具、extension | Node/CLI/服务端应用，想复用 pi 的完整设施 |
| `createAgentSessionRuntime` | 管理当前 active session，支持 new/resume/fork/import/reload 后重建运行时 | 需要多会话、切换 cwd、内置模式或复杂 UI |

“归一化入口”不是所有前端都用同一个类，而是不同外壳尽量接到同一层 agent 能力上，避免每个 workflow 重写一套 agent 逻辑。

---

## 一、`new Agent`：最小内核

`packages/agent/src/agent.ts` 的 `Agent` 是最底层对话引擎。

它关心：
- `state.messages`、`systemPrompt`、`model`、`thinkingLevel`、`tools`。
- `prompt()` / `continue()` / `steer()` / `followUp()` / `abort()` / `waitForIdle()`。
- `convertToLlm`、`transformContext`、`streamFn`、`onPayload`、`onResponse`。
- agent event 订阅。

它不内置 coding-agent 的这些设施：
- AuthStorage / ModelRegistry 的默认鉴权。
- ResourceLoader、skills、prompt templates、project context。
- SessionManager 的 JSONL 会话树。
- coding-agent 内置工具和 extension runtime。

所以 `new Agent` 适合浏览器端、自定义服务端、已有模型路由的系统。web-ui 示例就是直接 new `Agent`，再把它交给 `pi-chat-panel`。

---

## 二、`createAgentSession`：SDK 的常用入口

`createAgentSession(options)` 返回：

```ts
{
  session: AgentSession,
  extensionsResult: LoadExtensionsResult,
  modelFallbackMessage?: string
}
```

默认装配过程：

```text
AuthStorage.create
  -> ModelRegistry.create
  -> SettingsManager.create
  -> SessionManager.create
  -> DefaultResourceLoader.reload()
  -> findInitialModel + clampThinkingLevel
  -> new Agent({ convertToLlm, streamFn, transformContext, hooks })
  -> new AgentSession({ agent, resourceLoader, tools, extensionRunnerRef, ... })
```

一个关键分层：传给 core `Agent` 的 `streamFn` 是闭包。它在每次请求前通过 `modelRegistry.getApiKeyAndHeaders(model)` 取 key/header，再调用 `streamSimple`。也就是说，core Agent 不需要知道 auth 存在哪里；鉴权和 provider retry headers 是 SDK 层注入的。

`AgentSession` 在 `Agent` 外面补上：
- session 持久化和恢复。
- 内置工具、custom tools、extension tools。
- `_rebuildSystemPrompt`，把 tools、skills、project context、append prompt 合到 system prompt。
- extension events、commands、custom messages。
- compaction、model/thinking 切换、active tools。

最小 SDK 用法就是：建 session、订阅事件、发 prompt、dispose。

```ts
const { session } = await createAgentSession();
session.subscribe((event) => {
  if (event.type === "message_update" && event.assistantMessageEvent.type === "text_delta") {
    process.stdout.write(event.assistantMessageEvent.delta);
  }
});
await session.prompt("What files are in the current directory?");
session.dispose();
```

## 三、`AgentSessionRuntime`：内置模式真正复用的层

现在的 `main.ts` 不是只创建一个固定 session 后交给模式运行，而是先创建 `AgentSessionRuntime`。

runtime 负责：
- 当前 `runtime.session`。
- `newSession()`、`switchSession()`、`fork()`、`importFromJsonl()`。
- session replacement 后重新创建 cwd-bound services。
- 让模式层重新 bind extension UI、命令上下文和事件订阅。

这层很关键，因为 TUI/RPC/print 都可能触发 session 切换、reload 或 fork。没有 runtime，每个模式都要自己处理“旧 session 失效、新 session 重新绑定”的问题。

SDK 文档也提醒：如果只是单会话，直接用 `AgentSession`；如果需要替换 active session，就用 runtime。

## 四、运行形态

### print mode

`runPrintMode(runtime, options)` 是单发或少量消息的 CLI 模式：
- text mode 输出最终文本。
- json mode 输出 session events。
- 也会 bind extension command context，让 extension command、reload、fork 等在 print 环境里有基本行为。

### interactive mode

`InteractiveMode` 是 TUI 外壳：
- 负责输入框、补全、消息渲染、主题、快捷键。
- skill/template/extension commands 都在补全里组合。
- extension UI 的 `ctx.ui` 在这里有最完整实现。

### rpc mode

`runRpcMode(runtime)` 把 agent 暴露成 JSONL over stdio：
- stdin 每行一个 command。
- stdout 输出 response 和 session events。
- prompt 的 response 表示“已接受/已排队/已处理”，后续成功失败仍看事件流。
- RPC 也实现了一部分 extension UI request/response，比如 confirm/select/input/notify/status。

这适合 IDE、桌面应用、其他进程或自定义前端通过子进程驱动 pi。

### web-ui

`packages/web-ui` 是另一条路线：它直接用 core `Agent`，不是 coding-agent 的 `AgentSession`。

`ChatPanel` 是 lit web component：

```ts
@customElement("pi-chat-panel")
export class ChatPanel extends LitElement {
  async setAgent(agent: Agent, config?: ...) { ... }
}
```

示例里浏览器自己处理 IndexedDB session、API key prompt、artifact tools、JavaScript REPL、custom `convertToLlm`。这说明 core Agent 确实是 UI 无关内核，但 browser 端需要替代 Node 端的存储、鉴权和资源体系。

## 五、选择入口的判断

| 需求 | 推荐入口 |
|---|---|
| 只要 agent loop，其他设施自带 | `new Agent` |
| 要 pi 的 tools、skills、extensions、sessions | `createAgentSession` |
| 要多会话、fork、resume、reload 后重绑 | `createAgentSessionRuntime` |
| 要外部进程控制 | RPC mode 或直接用 SDK |
| 要浏览器组件 | `packages/web-ui` 的 `ChatPanel` + core `Agent` |

对自定义 UI bot 或 CLI，常见做法是从 `createAgentSession` 开始。如果后来需要“新会话/切换会话/fork 后继续保持 UI 和 extension 可用”，再上 runtime。

---

## 六、归一化入口是什么意思

归一化不是把所有工作流塞进同一个命令，而是把分散入口收敛到同一套 agent 能力：

- 同一套 turn loop 和工具调用语义。
- 同一套 session/history/context 投影。
- 同一套 skill/extension/resource 机制。
- 多个外壳只负责输入输出和 UI 差异。

这样做的收益是：CLI、TUI、RPC、bot、web UI 可以共享 agent 行为，差异只在 transport 和交互层。

---

## 一句话总结

pi 的应用入口分三层：`Agent` 是内核，`AgentSession` 是带 Node 设施的 SDK session，`AgentSessionRuntime` 是能替换 active session 的运行时。内置 print/interactive/rpc 复用 runtime；web-ui 直接复用 core Agent。构建 UI bot 或 CLI 时，先选对层级，再把工作流收敛到这套 agent 能力上。
