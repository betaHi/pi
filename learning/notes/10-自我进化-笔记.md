# 10 自我进化 · 学习笔记

> README 核心问题：agent 如何从反馈中更新规则、skills 或工具策略，并避免污染长期上下文？
> 证据来源：`resource-loader.ts`（`extendResources`/`reload`）、`agent-session.ts`（`setActiveToolsByName`/`appendCustomEntry`）、README 边界。
> 一句话：**pi 没有内置自我进化**（grep 坐实：无 eval/feedback/rollback）。它提供"能被更新的东西"——skills、prompt、工具策略、session 状态都可运行时改；但"从反馈评估→提出更新→验证→回滚"这套闭环是应用层的事。

---

## 题眼：自我进化不是"让模型随便改自己"

README 说得明确：自我进化不是放任模型改自己，而是**agent 基于反馈提出更新，经过验证后再写入，重点是边界、确认、回滚、可观测性**。

先坐实 pi 给了什么：grep `eval` / `feedback loop` / `reward` / `rollback` / `self-improv` —— **全空**。pi 不提供评估、反馈回路、回滚机制。

所以这一篇和 Memory 篇同构：**pi 提供"可被更新的原语"，不提供"更新的决策与控制"。** 下面把自我进化的四步（评估→更新→验证→回滚）和 pi 原语对上。

---

## 一、自我进化的四步，pi 各管到哪

| 步骤 | 做什么 | pi 提供 | 应用层要补 |
|---|---|---|---|
| **评估** | 从反馈判断"哪里该改" | 无 | 全部（指标、反馈信号、判断） |
| **更新** | 改 skills / prompt / 工具策略 | ✅ 有运行时写入点（见二） | 决定改什么、改成什么 |
| **验证** | 确认改完更好、没变差 | 无 | 全部（eval、回归、对比） |
| **回滚** | 改坏了退回去 | 无（但 append-only 天然可回溯） | 版本管理、回退触发 |

→ **pi 只在"更新"这步给了现成写入点，评估/验证/回滚是应用层的闭环。**

---

## 二、pi 提供的"更新"原语：运行时能改什么

自我进化要改的三类东西——规则/prompt、skills、工具策略——在 pi 里都有运行时写入点：

### 改 skills / prompt / 资源 —— `extendResources` + `reload`

`ResourceLoader`（resource-loader.ts）：
```ts
extendResources(paths): void      // 追加 skill/prompt/theme 路径
async reload(): Promise<void>     // 重新加载资源（settings、skills、extensions…）
```
- `extendResources` 后触发 `_rebuildSystemPrompt`（Context 篇第③触发点）——新 skill/prompt 进 system prompt。
- `reload` 重新读磁盘——改了 SKILL.md / AGENTS.md 文件后，reload 让新内容生效。

→ **进化"规则和技能" = 改磁盘上的 skill/prompt 文件 + reload，或 extendResources 加新的。**

### 改工具策略 —— `setActiveToolsByName`

```ts
setActiveToolsByName(toolNames): void   // 换当前激活的工具集，并重建 system prompt
```
→ **进化"工具策略" = 运行时改激活工具集**（如"这个任务发现某工具老出错，禁掉它"）。Tool 篇的两层准入（白名单 + active tools），active 这层可运行时调。

### 存进化状态 —— `appendCustomEntry`

```ts
appendCustomEntry(customType, data)   // 往 session 树存 extension 状态，不进 LLM 上下文
```
Session 篇的 `custom` entry：**存了但不进模型上下文**（`convertToLlm` 忽略 custom-entry）。适合存"进化系统自己的状态"（如某规则的版本、某次评估结果）——留痕但不污染对话。

---

## 三、"避免污染长期上下文"——pi 的机制怎么接住

README 特别强调"避免污染长期上下文"。pi 的几个设计正好对上：

- **`custom` entry 不进上下文**：进化系统的内部状态用 `appendCustomEntry` 存，`convertToLlm` 不投影它——状态留痕但模型看不到，不占 token、不干扰对话。（对比 `custom_message` 是**进**上下文的，两者一字之差、语义相反，Session 篇的 9 种 entry 里区分过。）
- **append-only 树天然可回溯**：Session 篇——什么都不删。进化改了什么、基于什么状态改的，都在树里留痕，天然支持"回看历史、回滚到某个点"。
- **基线 vs 每轮**（Context 篇）：`_baseSystemPrompt`（基线）和 extension 每轮临时改的 `state.systemPrompt` 分开——进化可以"这一轮试个新 prompt"而不动基线，验证好了再写进基线。这正是"提出更新→验证→再固化"的天然支点。

---

## 四、一个自我进化系统落到 pi 上会长什么样（推断）

【顺着原语推的设计，非 pi 源码，标清】

```
评估：extension 挂 turn_end/session_shutdown 事件收集反馈信号（成功率、用户纠正、报错）
      → 应用层判断哪条规则/工具策略该改（pi 不管评估逻辑）
更新：
  - 改规则/技能 → 改磁盘 skill/prompt 文件 + resourceLoader.reload()
  - 改工具策略 → setActiveToolsByName（禁用/启用某工具）
  - 存进化状态 → appendCustomEntry（版本、评估结果，不进上下文）
  - 试探性更新 → extension 每轮改 state.systemPrompt（不动基线）先验证
验证：应用层跑 eval / 回归（pi 不管）
回滚：append-only 树留痕 → 退回旧版本（版本管理应用层做）
```

pi 的边界：**它是"可被安全更新、且更新留痕不污染上下文的地基"，不是进化的大脑**。评估什么、改不改、改成什么、怎么验证回滚——全在应用层。

---

## 与 Memory 篇的关系

Memory 和自我进化用的是**同一批原语**、解决不同问题：
- **Memory**：记住信息 → 用 context hook / custom_message **注入**（进上下文）。
- **自我进化**：改变行为 → 用 extendResources/reload/setActiveTools **更新能力**，用 custom-entry **存状态**（不进上下文）。

一个往上下文里加内容，一个改产生上下文的规则。都建在 session 事件 + extension hook + resource loader 这套地基上。

---

## 一句话总结

pi 不内置自我进化（无 eval/反馈/回滚，grep 坐实）。它提供运行时更新原语：`extendResources`+`reload`（改 skills/prompt）、`setActiveToolsByName`（改工具策略）、`appendCustomEntry`（存状态、不污染上下文）；再加 append-only 树留痕、基线/每轮分离，天然支持"试探性更新 + 回溯"。但评估、验证、回滚触发这套闭环控制，是应用层要自己设计的。
