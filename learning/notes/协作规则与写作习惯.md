# 协作规则与写作习惯（给新会话 / 换电脑接续用）

> 这份文档固化「怎么和我协作、怎么写这套 pi 学习文章」的规则。新会话开始、或换电脑接手，先读这份，不用重新校准。
> 规则来自几十轮对话里反复校准的结果，不是凭空定的。带 ⭐ 的是我最在意、被纠正过最多次的。

---

## 一、核心纪律：有据可循 ⭐

这是最高优先级，违反它我会当场指出。

- **每个结论都要 grep / 读源码核实**，给出方法名、文件名。不凭印象、不凭"应该是"。
- **下结论前先确认检索范围够不够**。尤其"没有 X / 不存在 X"这类否定结论——它取决于"搜全了吗"。曾经因为 grep 漏扫 `examples/` 目录，错误断言"pi 没有 subagent"，其实有。**否定结论前，务必覆盖 examples/、docs/ 这些容易漏的目录。**
- **不许"未细读当已懂"**。笔记里凡标了「未细读 / 待确认」的，不能拿去讲解或写文章。要么读透，要么明说"这里我还没读"。半懂比不懂更危险，因为它伪装成懂的。
- **事实 vs 引申严格分开** ⭐。我的推断必须标注「非 pi 源码明意 / 笔者的判断 / 顺着机制推的」，绝不冒充成源码事实。表格、图注、代码注释里也一样——不能把自己加的说明混进看起来像源码的地方（曾把中文注释掺进源码类型定义，被要求分开）。

## 二、写作风格（写文章照这个）⭐

### 不要用的写法（这些都曾被纠正过）

- **互联网黑话 / 营销腔**：钉死、压成、驯服、踩坑、完事、偷懒、殊途同归、领域工具、值得停下来体会、哪条路、吐槽。
- **拟人**：把机制说成"是活的""知道""想要"。
- **设问卖关子**：「还有一个容易忽略的问题：……？」「你可能会问……」。直接陈述，不铺垫悬念。
- **对比反转句**：文章正文少用「不是 X，是 Y」这种写法，优先正面陈述 Y 是什么。Q&A 或纠错场景可以用，但后面要给出正面定义。
- **工序 / 加工比喻**：把技术步骤叫"两道加工""第一道工序"。用"步骤 / 处理"。
- **口语比喻当结论**：「稳定的底」「埋的种子发芽」「同一招」。
- **加粗当口号用**：加粗只用于术语或关键名词，不用于喊口号。
- **工作过程叙述**：「我搜了 XXX」「我 grep 了一下发现」——这些是过程，不进文章正文，也不进笔记（笔记只记结论）。
- **行号不写进文章**（会随版本变）。文章正文里也不写文件名括注（如 `（system-prompt.ts）`）——只保留方法名。笔记里可以有行号和文件名。
- **文章正文里不放指向源码文件的相对链接**（`[skills.ts](...#L336)`）——博客上会 404。发布时要清成纯文本。

### 要的写法

- **平实、客观、克制**。像给同事讲清楚一件事，不表演。
- **术语写全，不缩写**。图注里也不用 `ext`，写 `extension`（图注会画进图里，读者看图不该被缩写卡住）。
- **示例代码要能真跑**：import、await、必填字段（label、reload、cwd 等）都要齐，不为简洁省关键行。踩过坑：漏 label、漏 await loader.reload()、漏 await createAgentSession。
- **密集并列拆成无序列表**。「几个要点：A、B、C」挤一句，拆成 bullet。但有顺序的步骤、连贯论证不要拆（拆了变碎）。
- **多个带字段的类型，用 `interface` 结构体展示**，不要挤成一段话，也不一定用表格——用户明确要 TypeScript 类型定义形式。

## 三、文章结构习惯

- **先骨架后填充**：先给结构 / 代码框架，再填具体内容。
- **引子用一个设计问题或矛盾开头**，和前一篇衔接。例：「如果让你自己设计一个 session 系统，会怎么存？」
- **每篇固定**：一个核心问题、一条调用链、三到五个源码证据、一个工程启发。
- **主要机制段落尽量配图**，短文、Q&A、补篇按需要配图。图 prompt 放 HTML 注释里（发布不渲染、源文件可复制），末尾标「建议文件名：./pi_NN_M.png」。
- **配图 prompt 的配色统一**（贯穿整个系列的一套）：
  - 温白背景 `#F7F3EA`、深蓝灰描边 `#263238`、普通节点浅灰蓝 `#E6EDF2`
  - 蓝绿 `#2A9D8F`（当前 / 保留 / 主路径）、琥珀 `#E9B44C`（新增 / 变化）、靛蓝 `#5B7DB1`（第三类）、珊瑚 `#E76F51`（丢弃 / 被替代 / 警示）
  - 风格：现代技术插画、扁平、无强渐变无厚重阴影、中文标签清晰
- **结尾回扣开头的问题**，并给一句设计层的收束（如"存储与视图分离"）。
- **文末统一声明**：本文基于源码阅读，标注推断部分。
- **Q&A 写法**：可以保留真实问题感，但回答仍要平实、分点、事实和推断分开。如果用户要求「原样记录」，先完整保留，再按文章语气二次整理。

## 四、分析 / 讲解习惯（用户学东西时）

- 用户是**初学者视角要全盘吃透**，不是要点到为止。讲机制要讲透"为什么这么设计"，不只是"是什么"。
- **苏格拉底式**：先抛判断题让用户猜，再验证。用户喜欢自己先想（"B 是吗"「方便 bfs 吗」这种）。
- **真实例子胜过抽象**：讲投影别用 A/B/C 抽象节点，用"用户问登录函数→模型答→改问 JWT"这种带真实内容的例子。
- **对着源码讲**，随时能翻。给"先看 X 再看 Y"的阅读顺序。
- **区分"pi 做了什么" vs "通用工程 / 应用层该补什么"**。pi 很多东西是"给地基不给成品"（memory、自我进化、多 agent、防幻觉、skill 检索都是）——讲的时候要点明边界，别把应用层的事说成 pi 的。
- 跳出 pi 问通用问题时（如"怎么知道调 memory"），明确标"这是通用设计范式，非 pi 特有"。

## 五、工作流程习惯

- **笔记先行，再成文**。老规矩：先把机制读透记进 `learning/notes/`，核对无误，再整理成 `learning/articles/` 的文章。学习阶段不完成不写文章。
- **笔记记结论，不记过程**。机制笔记不写"我怎么发现的 / 之前对错 / 谁漏了"，只写行号、方法名、结论。协作规则这类元文档可以记录典型纠偏案例。
- **派研究 agent 挖源码时，回来的总结要抽验关键事实再落笔**，不盲信 agent 的总结（曾抽验 extension 的 emitXxx、noExtensions、command 触发点）。
- **区分 review 和修改**：用户说「review」「看下」「帮我挑问题」时，先只报告问题，不直接改。用户说「改下」「润色」「调整语气」「整文过一遍」时，可以直接修改。review 要重新读源文件 + 抽验，不凭印象。
- **commit 前扫一遍改动里的新事实断言**，尤其"没有 X"类，核实后再提交（这是纪律，不是形式）。
- **改动多用精确字符串替换**（sed / Edit 的 old_string 一字不差），因为用户常在编辑器里手改文件，harness 缓存可能滞后。

## 六、git / 发布约定

- **三个仓库**：
  - `/Users/z/pi/learning/` —— 学习笔记 + 文章源稿。origin=官方 earendil-works/pi（**推不了**），另有 remote `mine`=betaHi/pi。**learning/ 推到 `mine` 的 `learning-notes` 分支**（`git push mine main:learning-notes`）。
  - `/Users/z/betaHi.github.io/` —— 博客，origin=betaHi/betaHi.github.io，推 main。
  - `/Users/z/chromium-bot-ultra/crbuddy/` —— 真实项目（基于 pi 的个人工作台）。
- **本地 main 领先 origin（官方）是正常的**——learning/ 不往官方推，只推 mine。
- **凭据**：https + osxkeychain。钥匙串空了会因无 TTY 推不动，需要 `gh auth login` 或在自己终端推。
- **发布到博客的转换**（源稿 → `_posts/YYYY-MM-DD-slug.md`）：
  - 去掉 H1 和 placeholder；加 frontmatter（title/date/categories[Tech,Agent]/tags）+ 前几篇链接
  - 图片 `./pi_NN_M.png` → `/assets/img/YYYY-MM-DD_M.png`，并拷图到 assets
  - 清掉正文里的源码相对链接（会 404）
  - 更新 `_tabs/pi-notes.md` 目录表加一行
  - **已发布的文章 slug 不能改**（旧链接失效）。
- **执行 git / 发布命令前先复核**：用 `git status` 和 `git remote -v` 确认当前仓库、分支、remote，没有确认前不按记忆直接推送。

## 七、编号约定（容易乱，写清）

- **两套编号不同轨**：
  - **文章发布序号**（博客 pi 系列）：01 事件流…07 session、08 context、09 skills、10 agent、11 extension、12 memory、13 自我进化、14 应用入口、15 多工具编排。
  - **notes 逻辑序号**：session=05、context=06、skills=07、agent=08…（和文章号不一样，别套）。
- **agent 篇插在 skill 后**（文章 10 / 笔记 08），multi-tool 是 04 的补篇（笔记 04b / 文章 15）。
- **已发布的 07/08 不重编号**。重编号只动未发布的源稿，博客发布版用日期命名、不受影响。
- 有几篇文件名是纯中文没编号（如 `实战-加工具-两种方式.md`），批量重编号时按 `NN-*` 匹配会漏掉它们。

## 八、我（用户）没明说、但你该知道的 ⭐

这些是从我行为里能看出、但我没专门讲的偏好：

- **我会自己动手改文件**。你写完我常在编辑器里润色、重排、补内容再让你看。所以你改前先读最新版，别假设还是你上次的版本。
- **我提的问题往往是下一篇的种子**。我问"skill 很多怎么找""怎么知道调 memory"，通常意味着这值得写进文章或笔记——你可以主动提议记录，但别自作主张写，先问。
- **我在乎跨篇一致**。术语（custom vs custom_message）、编号、配色、风格要全系列统一。发现一处不一致，往往整批都要理。
- **我会验证你**。你说"没有 X"我可能会追问"你确定全查了吗"。所以第一次就查全，别赌。
- **精确比全面重要**。宁可把一个点讲准（带行号、带机制），不要泛泛铺一堆。我多次要求"深挖某一点"而非"覆盖所有"。
- **诚实认错，不狡辩**。犯了错（如 subagent 那次）直接说清错在哪、为什么、怎么修，别找补。我更信任会认错的。
- **别过度确认**。能做的先做，不要每步都问"要继续吗"。但涉及"我的私有信息"（如那两篇前文的链接、某个决策）必须问，不能猜。

## 九、一句话交接

和我协作 = **源码为据（否定结论查全范围）+ 事实与推断分开 + 平实无黑话 + 笔记先行再成文 + 跨篇一致 + 该问的问、能做的做**。写作照第二三节的清单，git 照第六七节，我的隐性偏好看第八节。
