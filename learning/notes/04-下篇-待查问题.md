# 查证结论

> 原则：**聚焦 pi core（packages/agent），coding-agent 必要时点到。**
> 记录格式：① core 机制（主结论，方法名+文件可查）② 应用层补充（coding-agent，点到即可）③ 我的引申（标注推论，非源码）。
> 顺序：按实际查证先后往下排。

## ④ 工具怎么提供的 / 从哪来 ✅

**core 机制（主）：**
- 工具对 core 来说就是 `agent.state.tools`（一个 `AgentTool[]`）。core 不关心工具从哪来、有几个，只管「拿到一组工具就能执行」。

**应用层补充（coding-agent，点到）：**
- 内置工具 **7 个，硬编码**：read、bash、edit、write、grep、find、ls（`allToolNames`）。非动态扫描/插件发现。
- 每个工具一个 `createXxxToolDefinition(cwd, options)` 工厂，按 cwd 造实例。
- 三套现成组合（源码无注释说明意图）：`createCodingToolDefinitions`(read/bash/edit/write)、`createReadOnlyToolDefinitions`(read/grep/find/ls)、`createAllToolDefinitions`(全 7 个)，经 `sdk.ts` re-export，给哪些由开发者定。
- extension / SDK 也能加工具（来源汇总见 ① 的 `_refreshToolRegistry`）。

**我的引申（非源码意图）：**
- 「只读组合是为安全设计」查无实据；「能力消除优于运行时防御」是通用原则，非 pi 表述。

## ② 怎么判断意图 / 模型怎么知道有哪些工具 ✅

**core 机制（主）：**
- 工具走 API 原生 **tools 字段**（与 systemPrompt、messages 平级），不是混进 prompt 文本。
  - 路径：`context.tools` → `agent-loop.ts`（streamAssistantResponse 构建 Context）→ provider 转成 `params.tools`（anthropic 例：`convertTools()`）。
- 边界：「决定调哪个工具」是模型的推理，core 里没有、也没有 `decideIntent()`。harness 只负责把工具摆进请求。

**应用层补充（coding-agent，点到）：**
- system prompt 里另有 "Available tools" 列表 + guidelines（`system-prompt.ts` 的 `buildSystemPrompt()`），只放一句话 snippet，且只有给了 snippet 的工具才出现（`visibleTools` 过滤）。

**我的引申（非源码）：**
- 「tools 字段=调用依据、snippet=概览、两路叠加判断意图」——我的解释，源码没这么写。

## ③ 权限怎么注入 / 默认什么策略 ✅

**core 机制（主）：**
- 拦截点 `beforeToolCall` 是 **core 的能力**：`agent.ts` 里 `public beforeToolCall?` 公开属性，`new Agent({ beforeToolCall })` 可传入，loop config 带上生效。
- **结论：只用 pi core 就能做权限拦截**，给 `agent.beforeToolCall` 赋个函数即可，返回 `{ block: true }` 拦、`undefined` 放行。不需要 extension。

**应用层补充（coding-agent，点到）：**
- coding-agent 在 `agent-session.ts` 给 `beforeToolCall` 挂了个函数，自己不写策略，只转发给 extension 的 `tool_call` 钩子。
- 默认无 extension 处理器 → 放行（默认不拦）。
- extension 钩子抛错时选择 throw 阻止执行（fail closed，"Extension failed, blocking execution"）。

**默认策略已确证（源码层面）：coding-agent 默认不拦任何工具、不自带权限确认。**
- `extensions/` 目录无任何成品扩展，extension 全靠外部路径加载，开箱为空。
- core/*.ts grep `approv|confirm|dangerous|permission` 只命中白名单 `allowedToolNames`，无执行前确认逻辑。
- interactive 模式的 `confirm` 是给 extension 用的通用对话框（`showExtensionConfirm`），非内置危险命令确认。`tool_call` hook 唯一消费点是 `agent-session.ts` 那个转发，没有任何地方默认挂拦截。
- 边界：仅就本仓库源码而言；发行版若在别处带默认确认配置，不在此结论内。

## ① 工具多了怎么处理（含 extension 来源）✅

**core 机制（主）：**
- core 不管「多不多」——它只拿到 `agent.state.tools` 一个数组，有几个就把几个全放进请求的 tools 字段（数组内容已由 coding-agent 的白名单筛过，见下）。**core 自身没有任何工具数量管理。**

**应用层补充（coding-agent，点到）：**
- 工具集汇总在 `_refreshToolRegistry()`：三个来源合进一个以工具名为 key 的 Map —— ① 内置 `_baseToolDefinitions` ② extension 注册 `getAllRegisteredTools()` ③ SDK 直接塞 `_customTools`。同名后者覆盖前者。
- **准入闸**：`_allowedToolNames` 白名单 + `isAllowedTool()`。不在白名单的工具，三个来源一律过滤掉，根本不进 registry（注册 50 个、白名单 5 个 → 最终只有 5 个）。这是比 beforeToolCall 更前置的控制（压根不让工具进，而非执行时拦）。
- 合并时顺带收集每个工具的 `promptSnippet` / `promptGuidelines`（接 ② 那题：system prompt 的 Available tools 列表就用这些 snippet）。

**pi 没有做的（全文 grep 无 maxTool / tool limit / lazy tool / 分组，确证）：**
- ❌ 工具数量上限 / top-N 截断
- ❌ 按需懒加载工具
- ❌ 工具分组 / 折叠
- 即：过了白名单的工具**全量暴露**给模型。pi 只提供「选哪些进来」（白名单），不解决「白名单本身太大、token 爆」——那是应用层自己的权衡。

**extension 是什么（一句话 + 类名路径，够回查即可）：**
- 作用：不改 pi 源码，就能往 agent 生命周期插逻辑、往系统加工具/provider/命令。几乎每个生命周期节点都开了 hook。
- 关键类型，都在 `packages/coding-agent/src/core/extensions/`：
  - `ExtensionAPI`（types.ts）：注册 API，`registerTool()` / `registerCommand()`。
  - `ExtensionRuntimeState`（types.ts）：`registerProvider()`（03 篇 hello.mjs 改 baseUrl 用的）。
  - `ExtensionEvent`（types.ts）：所有 hook 事件的联合类型（含 ToolCallEvent=③权限、ContextEvent=07memory 等）。
  - `ExtensionRunner`（runner.ts）：事件分发器，`emit()` / `emitToolCall()` / `emitContext()`。
  - `ExtensionContext`（types.ts）：传给每个 handler 的上下文。

**我的引申（非源码意图）：**
- 「pi 只给白名单、不做数量管理，符合机制/策略分离」——引申。
- 「工具特别多时，按需暴露要应用层自己补（pi 没做这层）」——对照 Claude Code/MCP 的引申，非 pi 表述。

## 框架问题（上篇带读已碰，此处按 core/事实 归档）

均在 `packages/agent/src/agent-loop.ts`（core）。

### 保证一：怎么守住「模型不执行、程序执行」的边界
- 事实：`runLoop` 里**生成与执行是两个分开的调用**——`streamAssistantResponse()` 只生成；`message.content.filter(c => c.type === "toolCall")` 程序识别意图；再 `executeToolCalls()` 执行。没有 toolCall 就不进执行。
- 即：模型产出里只有「toolCall 数据」，执行动作完全由 loop 发起。边界靠「生成/识别/执行分三步」物理隔开。

### 保证二：并行时副作用工具不互踩
- 事实：`executeToolCalls` 开头 `hasSequentialToolCall = toolCalls.some(... executionMode === "sequential")`；只要有一个 sequential（或 config.toolExecution=sequential）→ 整批走 `executeToolCallsSequential`（排队），否则 `executeToolCallsParallel`。
- 并行的正确性细节：`executeToolCallsParallel` 用 `Promise.all` 并发执行，但结果消息按 `orderedFinalizedCalls` **原顺序**生成回传（**并发执行、顺序回传**）。
- 即：写类工具声明 sequential，一个就让整批排队；只读工具默认并行但结果顺序不乱。

### 保证三：失败不带崩（四类错误都变结果，不 throw 穿透）
- 事实：四类错误都走 `createErrorToolResult` + `kind:"immediate"`/`isError:true`，不向 loop 外抛：
  - 工具找不到（`prepareToolCall`）、参数校验失败（catch）、beforeToolCall 拦截（block）、工具执行抛错（`executePreparedToolCall` 的 catch）。
- 即：错误变成一条 toolResult 放回上下文，模型下一轮可读到并自我修正，agent 不中断。

### 保证四：结果怎么回到模型不断片
- 事实：执行结果 `createToolResultMessage()` 打包成 `ToolResultMessage`，由 `runLoop` 用 `currentContext.messages.push(result)` 放回上下文（执行器不自己写状态，见 ④ 的状态归属）。
- 即：下一轮 `streamAssistantResponse` 时结果已在上下文，模型接着推理。`toolCallId` 负责把结果和原请求配对。

## ⑥ 真实工具印证（read / bash，各取一个代表机制）✅

文件：`packages/coding-agent/src/core/tools/`（read.ts、bash.ts、truncate.ts）。

### read —— 代表挑战：输出可能超大
- 默认上限：2000 行 或 50KB，先到先截（`truncate.ts` 的 `DEFAULT_MAX_LINES` / `DEFAULT_MAX_BYTES`，`truncateHead()`）。
- 截断后**显式告诉模型**：result 带 `truncation` 字段，渲染成明确提示，如 `[Truncated: showing 2000 of 8500 lines]`（read.ts）。
- 工具 description 里写明**续读手段**：`Use offset/limit for large files ... continue with offset until complete`。
- 印证的点：截断不能默默做（否则模型以为读全了），要 **截断 + 声明截断 + 给续读手段**。和上篇「错误要变成模型能读的反馈」同思路。

### bash —— 代表挑战：边跑边出、可能长跑、有副作用
- 流式：`child.stdout/stderr.on("data", onData)`，输出一来就送出（接到上篇的 `onUpdate` → `tool_execution_update` 事件），非等结束才给。
- 超时：`timeout` 到 → `killProcessTree(child.pid)`（bash.ts）。
- 可中断：`signal.aborted` → `killProcessTree`，用户 abort 能真停。
- 杀**整棵进程树**（非 `child.kill()`）：bash 可能 spawn 子进程，只杀父会留孤儿。
- 印证的点：执行类工具光能跑不够，还要管 **实时输出 + 超时强停 + 可中断 + 停得干净**。

### 对比
| | read | bash |
|---|---|---|
| 挑战 | 输出超大 | 边跑边出 / 长跑 / 有副作用 |
| 对策 | 截断+声明+续读 | 流式 onData + 超时 kill + signal 中断 + 杀进程树 |
| 通用点 | 截断也要回传给模型 | 执行类工具要管实时性与失控停止 |
