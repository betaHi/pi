上一篇 memory 讲的是"往上下文里加内容"。这一篇讲另一件事：**改产生上下文的规则**——让 agent 根据反馈更新自己的规则、skills 或工具策略。

和 memory 一样，先说边界：自我进化不是 pi 的内置功能。而且这里有个更需要说清的点——自我进化不等于"让模型随便改自己"。它是 agent 基于反馈提出更新，经过验证后再写入，重点在边界、确认、验证、回滚。pi 提供的是"可被更新的东西"，更新的决策和控制是应用层的事。

## 一、pi 没有内置自我进化

检索整个仓库：搜 `eval`、`evaluation`、`feedback loop`、`reward`、`rollback`、`self-improve`，没有相关实现。

所以 pi 不提供评估、反馈回路、回滚机制。这一篇和 memory 篇同构：pi 提供"可被更新的原语"，不提供"更新的决策与控制"。

一个自我进化系统通常有四步——评估、更新、验证、回滚——pi 只在"更新"这一步给了现成的写入点。

## 二、更新原语：运行时能改什么

自我进化要改的三类东西——规则和 prompt、skills、工具策略——在 pi 里都有运行时的写入点。

**改 skills 和 prompt**，靠资源加载器的两个方法：一个追加新的 skill / prompt / theme 路径，一个重新加载资源。追加之后会触发 system prompt 重建（Context 篇讲过的第三个触发点），新的 skill 或 prompt 就进了 system prompt；重新加载则会重新读磁盘，改了 SKILL.md 或 AGENTS.md 文件后，让新内容生效。

所以更新"规则和技能"，就是改磁盘上的 skill / prompt 文件再重新加载，或者追加新的资源路径。

**改工具策略**，靠 `setActiveToolsByName`——运行时换掉当前激活的工具集，同时重建 system prompt。比如某个任务里发现某个工具老出错，就把它从激活集里去掉。这对应 Tool 篇讲的两层准入里的 active tools 那一层，是可以运行时调整的。

**存进化自己的状态**，靠 `appendCustomEntry`——往 session 树里加一个 `custom` 类型的 entry。这种 entry 存了但不进模型上下文（Session 篇的 9 种 entry 里，`custom` 是被投影忽略的那种）。适合存进化系统自己的状态，比如某条规则的版本号、某次评估的结果，留痕但不占用模型的上下文。

## 三、"避免污染长期上下文"，pi 的哪些设计接得住

README 特别强调"避免污染长期上下文"。pi 有几个设计正好对上这个要求。

**`custom` entry 不进上下文**：进化系统的内部状态用它存，投影时被忽略，模型看不到——状态留痕，但不占 token、不干扰对话。这里要和 memory 篇的 `custom_message` entry 区分开：两者都是 session 树上的节点，但 `custom_message` entry 会被投影进上下文，`custom` entry 不会。一个用来注入内容给模型看，一个用来存状态给应用层自己用。

**append-only 树天然可回溯**：Session 篇讲过，什么都不删。进化改了什么、基于什么状态改的，都在树里留痕，天然支持回看历史、回滚到某个点。

**基线和每轮分离**：Context 篇讲过，`_baseSystemPrompt` 是基线，extension 每轮可以临时改 `state.systemPrompt`，不动基线。这正好是"提出更新、先验证、再固化"的支点——可以这一轮试个新 prompt，验证好了再写进基线，不好就下一轮自动还原。

这三个设计不是为自我进化专门做的，但都能被它利用：状态存得下又不污染上下文，改动留得下痕迹又能退回，试探性更新能和稳定基线分开。

## 四、一个自我进化系统落到 pi 上会是什么样

下面这段是顺着原语推的设计，不是 pi 的源码，标清楚。

```
评估：extension 挂 turn_end / session_shutdown 事件，收集反馈信号（成功率、用户纠正、报错）
      → 应用层判断哪条规则或工具策略该改（pi 不管评估逻辑）
更新：
  - 改规则和技能 → 改磁盘上的 skill / prompt 文件 + 重新加载
  - 改工具策略 → setActiveToolsByName 禁用或启用某工具
  - 存进化状态 → appendCustomEntry 存版本、评估结果，不进上下文
  - 试探性更新 → extension 每轮改 state.systemPrompt，先验证再固化
验证：应用层跑评估、回归对比（pi 不管）
回滚：append-only 树留痕 → 退回旧版本（版本管理应用层做）
```

pi 的边界：它是"可被安全更新、且更新留痕不污染上下文的地基"，不是进化的决策者。评估什么、改不改、改成什么、怎么验证和回滚，全在应用层。

## 五、和 memory 的关系

memory 和自我进化用的是同一批地基——session 事件、extension hook、资源加载——但解决不同的问题：

| | memory | 自我进化 |
|---|---|---|
| 目的 | 记住信息 | 改变行为 |
| 手段 | context hook / custom_message **注入**（进上下文） | extendResources / setActiveTools **更新能力**，custom entry **存状态**（不进上下文） |
| 方向 | 往上下文里加内容 | 改产生上下文的规则 |

一个往上下文里加东西，一个改生成上下文的规则。两个都建在同一套地基上，这也说明 pi 的分层是自洽的：session 事件、extension hook、资源加载这几样基础能力，能同时支撑起 memory 和自我进化两种应用层系统。
